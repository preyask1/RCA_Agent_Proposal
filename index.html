What this is about

Every data issue today — a Power BI discrepancy, a Pulse mismatch, a Databricks pipeline failure, an ADF ingestion error — requires a senior engineer to manually trace evidence across four disconnected systems. That takes 3–6 hours per incident. This agent automates the entire investigation, produces a structured RCA report, and waits for a human to confirm before posting anything to Jira.

Problem
Manual cross-system investigation consuming 3–6 hrs of senior engineer time per incident, with no consistent RCA format
Solution
Foundry-hosted agent: triggered by a Jira ticket, investigates all four data planes, posts a structured RCA report
Constraint
Read-only across all systems. One gated write: the Jira comment, posted only after human review and confirmation

Is this feasible on Foundry?

Yes — and the timing is good. Claude reached general availability in Microsoft Foundry in June 2026. Hosted agents went GA in July 2026. The MCP connector for Claude on Azure shipped in August 2026. Everything this agent needs is live now, not on a roadmap.

GA · June 2026
Claude on Azure
Anthropic models hosted on Azure with Entra ID auth, Azure billing, and the Messages API. Prompts stay within Azure perimeter.
GA · July 2026
Hosted agents
Bring your own code and framework. Foundry runs it as a container with managed endpoint, scaling, session state, and observability.
Live · August 2026
MCP connector + tool search
Structured outputs, web search, web fetch, and MCP connector now available for Claude on Azure-hosted deployments.

One known limitation

Computer use and browser toolsets are not available on Azure-hosted Claude deployments. This is not a blocker — the agent is designed to use log-based evidence, not browser screenshots. If browser automation is ever needed, it would route through the "Hosted on Anthropic" option instead.

What about Graph databases and RAG in the future?

Both are natural extensions of this agent and are fully supported in the Azure ecosystem. The agent as designed today is a live-query agent — it hits Databricks, Fabric, and ADO in real time. Once 3–6 months of confirmed RCA cases accumulate, the architecture can be extended:

Phase 1–3
Live-query agent
Hits Databricks, Fabric, ADO in real time for every investigation. Builds the case library.
Phase 4
RAG on case library
Retrieval before investigation
Before querying Databricks, retrieves top 3 similar past cases. Known root causes resolved in under 1 minute.
Phase 4
Graph database
Lineage as a graph
Build a knowledge graph of tables, measures, notebooks, and pipelines. Lineage trace becomes a single graph query — no live SQL needed.
Phase 5
GraphRAG
Cheaper + faster
LazyGraphRAG reduces indexing cost to 0.1% of full GraphRAG. Multi-hop queries across Jira tickets, RCA reports, and ADO history.

Identity and security model

Two service principals. One Key Vault. No credentials in any repo, image layer, or config file. Databricks access is enforced at the platform level (UC grants), not just by agent instruction.

What the agent never does

Enforced by UC grants, SP role assignments, and the agent's permission allow-list — not just by instruction.

✕
Write, commit, or push to any ADO repo
✕
Modify any Databricks table, schema, job, or cluster
✕
Publish a Power BI model or trigger a dataset refresh
✕
Trigger an ADF pipeline run or modify a linked service
✕
Post to Jira without a human reviewing and confirming first
✕
Use browser automation or reproduce named-user screenshots
✕
Store any credential in a repo, image, or committed config file
✕
Run INSERT, UPDATE, DELETE, DROP, or MERGE on any database

Risks and mitigations

RiskLikelihoodMitigation
Fabric SP API access disabled by tenant policy Medium Validate "Service principals can use Fabric APIs" in Phase 1 — blocks Phase 2 if unresolved
Databricks UC grants not tightened before go-live Medium Enforce SELECT only on gold.* and pulse.* before Phase 2; remove prompt-level constraint
Azure SQL access not provisioned for Pulse persona Medium Confirm SP-B db_datareader role on mnkDnAIdb in Phase 1; Pulse-Investigation depends on it
Container restart loses rca-cases/ history Low Persistent volume mounted; cases committed to git branch after each investigation
ADF REST scope blocked by subscription policy Low Validate SP-B Reader role on ADF resource in Phase 1 — well before Phase 3 starts
Human confirm step bypassed under time pressure Medium Gate enforced in code — Jira write is not in the agent's allow-list; only exposed via front end confirm action
Jira bot lacks DP project permissions Low Create bot and confirm DP read + comment access in Phase 1 before Phase 2 starts
